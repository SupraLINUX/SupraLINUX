# SupraLayers — paquetes nativos transaccionales
Fuentes: [rpm-ostree handbook](https://github.com/coreos/rpm-ostree/blob/main/docs/administrator-handbook.md), [Arkdep usage](https://docs.arkanelinux.org/arkdep/usage/), [AUR](https://wiki.archlinux.org/title/Arch_User_Repository), [clean chroot](https://wiki.archlinux.org/title/DeveloperWiki:Building_in_a_clean_chroot), [Arch Archive](https://wiki.archlinux.org/title/Arch_Linux_Archive), [Distrobox](https://distrobox.it/).
## Requisito
Usuario puede elegir paquetes Arch oficiales adicionales, AUR o locales compatibles en host; no solo drivers. Usar paquetes .pkg.tar.zst y Pacman/libalpm existentes, no RPM ni gestor nuevo. Apps convencionales Flatpak/AppImage; AUR integrado/restringido/host seleccionable, con explicación de efectos. Ninguna modificación del sistema activo por mecanismo oficial. AUR no soportado oficialmente por Arch, riesgo informado. No acceso privilegiado genérico para agentes.
## Modelo de estado
BaseRelease(id, architecture, repository_snapshot, package_lock, digest, trust); LayerIntent(id, requested_package, origin, recipe_revision, desired_version_policy, scope, authorization); BuiltArtifact(hash, package_version, source_hashes, dependencies, target_release, build_report, local_provenance); Deployment(id, base_release, resolved_effective_packages, layer_results, kernel_release, boot_asset_ids, config_revision, status). Registro de intención separado de capas efectivas por despliegue; estados staged/booting/good/failed/retired y requested/blocked/installed/removal-pending. Tras rollback mostrar lo que realmente está instalado y qué intención queda pendiente. No afirmar confianza oficial para paquetes firmados localmente. Estado persistente transaccional y reconciliación al boot desde evidencia del despliegue real.
## Flujo
Plan/resolver snapshot -> preview origen, dependencias, conflictos, cambios de base, permisos, espacio y reinicio -> aprobación humana -> construir AUR sin privilegios de host en entorno separado (PKGBUILD, .install, patches, fuentes y checksums revisados; VCS fijado a commit; clean chroot no sandbox) -> stage nuevo root con pacman y metadata consistente -> ejecutar hooks legítimos en contexto de destino acotado, no en activo -> comprobar módulos/boot/config -> commit manifest + estado y boot entry con orden recuperable -> boot assessment -> good o rollback. Cancelación antes de commit deja activo intacto. Hooks con efectos externos requieren aislamiento y revisión; no asumir transacción de filesystem cubre scripts/servicios. Validar arquitectura, dependencias transitivas, conflictos, reemplazos y archivos; no remover componente crítico silenciosamente. No permitir mezcla rolling/snapshot. AUR construido contra mismo destino; dependencias AUR pin explícito. Reutilizar cache solo si hash y contexto compatibles.
## Actualizar
Reaplicar intención a nueva base, resolver/rebuild, mostrar incompatibilidades. Si falla, no activar capa parcial sin aprobación. Permitir quitar capa incompatible o arrancar base oficial sin capas tras consentimiento; correcciones críticas no deben quedar bloqueadas indefinidamente por paquete no oficial. No eliminar datos de usuario. Mantener último good y base oficial recuperable; espacio estimado antes. Pacman db, módulos, kernel y /etc por deployment (no DB pacman global compartida). Distinguir rollback elegido por usuario de rollback de metadata no autorizado.

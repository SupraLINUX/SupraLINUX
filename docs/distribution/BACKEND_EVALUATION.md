# Comparativa técnica de despliegues
Consulta documental 2026-11-24; no pruebas ejecutadas. Fuentes: [Arkdep README](https://github.com/arkanelinux/arkdep), [uso](https://docs.arkanelinux.org/arkdep/usage/), [arquitectura](https://docs.arkanelinux.org/arkdep/how-it-works/), [RAUC reference](https://rauc.readthedocs.io/en/stable/reference.html), [RAUC adaptive](https://rauc.readthedocs.io/en/stable/advanced.html), [sysupdate.d](https://www.freedesktop.org/software/systemd/man/latest/sysupdate.d.html), [OSTree atomic upgrades](https://github.com/ostreedev/ostree/blob/main/docs/atomic-upgrades.md), [rpm-ostree](https://github.com/coreos/rpm-ostree/blob/main/docs/administrator-handbook.md), [blendOS](https://blendos.co/install/post-install/intro/), [Solera](https://soleralinux.org/).
| Candidato | Fortalezas | Brecha / incertidumbre |
|---|---|---|
| Arkdep | Arch, Btrfs, image build, múltiples deployments, GPG, layering | README advierte madurez; tracker puede divergir tras rollback, capas pueden omitirse, layering puede tocar actual: comprobar y adaptar |
| RAUC | bundles firmados, slots A/B, health mark-good/bad, adaptive streaming | no compone paquetes Arch por sí mismo; slots/boot integration y capas locales requieren diseño |
| systemd-sysupdate | recursos versionados coordinados, manifest firmado, UKI/verity, particiones o archivos | no resuelve AUR, configuración/migraciones y composición de local layers |
| OSTree | árboles versionados, merge /etc, contenido reutilizado | integración de pacman con modelo OSTree y capas requiere esfuerzo; rpm-ostree es referencia no backend Arch directo |
| blendOS | paquetes AUR, kernel/driver declarativos en Arch | evaluar coherencia de snapshots, trust, rollback y estado; no adoptar distro completa |
| Solera | declara snapshots Arch y layering | referencia emergente; comprobar código, madurez, licencia y pruebas antes de adoptar |
Preferencia profesional: prototipo Arkdep primero; reutilizar lo que cumpla. No adoptar su modo de layering sobre activo ni fallback silencioso. Adaptar mediante patch/fork con inventario de licencia y fuente; no duplicar motor si adapter suficiente. Si gates críticos fallan, comparar RAUC/sysupdate con misma carga y operación; OSTree solo si brecha justifica. No combinar múltiples autoridades de despliegue.
## Benchmark de decisión
Misma base Arch, snapshot y VM con disco de prueba; comparar tiempo de build/stage/boot/rollback, bytes download y disco, memoria, datos, recuperación y esfuerzo de mantener cambios. Gates no compensables: firma, no mutar activo, conservar known-good, estado efectivo coherente, boot recovery offline, módulo opcional, falta de espacio y power-cut. Probar corte en descarga, extract, hooks, manifest, boot entries y confirmación; reinicio tras cada punto. Registrar commit/licencia/backend versión, logs y resultados. D00 sigue NOT_RUN.
## Revisión de código 2026-11-24
[ARKDEP_SOURCE_REVIEW.md](ARKDEP_SOURCE_REVIEW.md) fija commit, líneas y diferencias. Solera es downstream de Arkdep (no un motor alternativo independiente), su CLI delega layer/unlayer en Arkdep. Shanios referencia de Btrfs blue/green y persistencia selectiva; evaluar, no adoptar su política completa. bootc permite builds OCI locales y staging, pero soporte Arch/pacman y layering deben demostrarse; su documentación distingue backend OSTree y composefs en detección de fallos. systemd-sysupdate soporta targets subvolume Btrfs y boot counting; sigue sin resolver composición de paquetes. Priorizar Arkdep como PoC, sysupdate como alternativa de bajo nivel si adaptación invade todo el motor, RAUC si slots fijos resultan preferibles. No implementar tres backends en paralelo.

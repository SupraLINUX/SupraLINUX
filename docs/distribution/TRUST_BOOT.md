# Firma, Secure Boot, UKI y cifrado
Fuentes: [Arch package signing](https://wiki.archlinux.org/title/Pacman/Package_signing), [Arkdep repositories](https://docs.arkanelinux.org/arkdep/repository/), [TUF spec](https://theupdateframework.github.io/specification/latest/), [boot assessment](https://systemd.io/AUTOMATIC_BOOT_ASSESSMENT/), [root discovery/UKI](https://systemd.io/ROOTFS_DISCOVERY/), [Secure Boot Arch](https://wiki.archlinux.org/title/Unified_Extensible_Firmware_Interface/Secure_Boot), [systemd-cryptenroll](https://www.freedesktop.org/software/systemd/man/latest/systemd-cryptenroll.html), [dm-verity](https://docs.kernel.org/admin-guide/device-mapper/verity.html).
## Fronteras distintas
Paquetes: validar firma y confianza Arch, repos propios con keyring propio; no desactivar validación al fallar. Release: firmar manifest/version/channel/hash/size/compatibility y artefactos; GPG Arkdep obligatorio si adoptado. TUF candidato para metadata versionada, expiración, delegación y rotación; usar implementación revisada, no crypto propia. Boot: Secure Boot verifica componentes EFI firmados; UKI reúne stub, kernel/initrd y parámetros según diseño. Firma de módulo y enforcement del kernel separados. Btrfs RO y checksums no equivalen a autenticidad runtime; evaluar dm-verity con imagen de bloques/roothash confiable si modelo elegido, no prometerlo sobre cualquier subvolumen. Cifrado LUKS2 protege datos en reposo, no garantiza integridad de código ni protege datos ya desbloqueados.
## Claves
Offline root, release signing controlado, claves de metadata online limitadas, rotación/revocación y recuperación; threshold según equipo real. Nunca guardar claves privadas en Git o CI de contribuciones. Clave local de personalización separada de oficial, enrollment explícito; firmar capa local no significa que sea auditada. No proporcionar a agentes acceso directo a claves ni autoaprobar módulos. Mantener certificados firmware necesarios para otros sistemas/dispositivos; no reemplazarlos automáticamente. Plan de firma comercial/distribución Secure Boot todavía no resuelto.
## Arranque y recovery
systemd-boot/UKI candidato UEFI. Boot counting y health gate con intentos acotados, no marcar good solo por kernel; comprobar almacenamiento, login y compositor mínimo sin exigir red. Conservar boot assets antiguos y espacio, no asumir FAT/ESP transacción perfecta. Rollback manual/offline y recovery externa. Evitar downgrade remoto involuntario; recuperación local deliberada de versión anterior con aviso de vulnerabilidades. Verificar firma de módulo según política real y kernel exacto. Pruebas con OVMF/TPM virtual y hardware, sin sustituir claves reales en fase experimental.
## LUKS2
Opción recomendada en instalación, frase de paso y recovery key offline; TPM2/FIDO2 opcionales según hardware y preferencias. Política PCR firmada candidata para permitir varios despliegues autorizados, testear actualización, rollback, reset/firmware y pérdida de TPM; no eliminar passphrase válida al enrollar. Backup de header separado y protegido, explicar consecuencias de pérdida de claves. No exponer frases o recovery keys en logs, agentes o telemetría. No prometer desbloqueo transparente universal.
[Release lab](RELEASE_LAB.md): separar claves de prueba de producción, evaluar shim review y transición Microsoft UEFI CA 2023, SBAT y revocaciones. No garantizar firma pública. Firmware puede alterar PCR y confianza, rollback OS no revierte firmware.

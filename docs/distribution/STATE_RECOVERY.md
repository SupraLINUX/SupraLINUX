# Estado persistente, configuración y recuperación
Fuentes: [OSTree deployments](https://ostreedev.github.io/ostree/deployment/), [Btrfs subvolumes](https://btrfs.readthedocs.io/en/stable/btrfs-subvolume.html), [send/receive](https://btrfs.readthedocs.io/en/stable/Send-receive.html), [restic](https://github.com/restic/restic/blob/master/doc/manual_rest.rst), [restic check](https://github.com/restic/restic/blob/master/doc/045_working_with_repos.rst).
## Clasificación propuesta, layout pendiente
Root/usr + pacman DB + kernel/modules por despliegue. /etc defaults versionados y configuración local merge de tres vías (defaults antiguos, local, defaults nuevos) inspirado en OSTree; no overwrite ciego ni merge genérico de secretos. Conflicto visible y revisión; cuentas, UID/GID, fstab, crypttab, red, claves máquina requieren política por dominio, no copiar indiscriminadamente. /home y documentos persistentes. Flatpak system/user storage, portables, contenedores y datos app persistentes por diseño. /var por categoría: DB de paquetes por imagen; logs/cache recreables o persistentes con cuotas; DB de servicios con migración compatible, versión de schema y backup. No compartir /var indiscriminadamente. /run efímero. ESP boot assets versionados.
Migraciones: expand/contract cuando viable; no ejecutar migración irreversible sin backup/recovery; si no hay compatibilidad backward, impedir activación o informar y preparar restauración de datos de servicio consentida. Rollback OS no revierte documentos/apps personales; rollback de una app individual tampoco garantiza datos compatibles. Btrfs nested subvolumes no se incluyen automáticamente en snapshot; inventariar todos. Snapshots CoW ocupan espacio con cambios, medir y aplicar cuotas/retención; no eliminar último good por limpieza. No prometer recuperación ante fallo físico con snapshot local.
## Recovery offline
Entrada anterior + modo seguro sin extensiones/capas cuando sea posible + medio live verificable. UX permite diagnosticar, arrancar anterior, quitar capa en próximo deployment, montar datos cifrados con clave válida, exportar diagnóstico redactado, reparar boot o reinstalar base conservando home solo con plan explícito. No ejecutar reparaciones destructivas automáticas, no reset de contraseña o bypass. Probar ausencia red, disco lleno, ESP dañado (medio externo), config incompatible, corrupción de datos y recuperación de claves. Recuperación de despliegue no es backup.
## SupraBackup
Equivalente funcional Time Machine opcional, usar restic (cifrado/dedupe/restore) o Borg tras evaluación, no crear formato backup propio. Destino disco externo/NAS compatible, opcional remoto explícito; al menos una copia independiente/desconectable; retención configurada, exclusiones de caches/modelos gigantes opt-in, permisos y restauración de muestra con hash. Snapshot Btrfs puede estabilizar fuente; coherencia de DB requiere método propio. Restore a ubicación alternativa y preview antes de sobrescribir. Backup de configuración y manifest de capas permite reconstrucción, no replicar secretos sin protección. Verificar integridad y restauración real; no afirmar éxito solo por salida del job.

## Read-only deployment experiment (NOT_RUN until CI)
Independent continuation of verified additive layer: create disposable snapshots of staged and layer, set Btrfs subvolume ro=true and mount / ro; preserve approved parent image. Separate private 1 GiB Btrfs state disk with explicit subvolumes for /home, /var/log, /var/cache, /var/lib/systemd and /var/tmp; no shared /var, package database remains in deployment; /run and /tmp tmpfs. Use stable machine identity only within this disposable test, discard copied random seed. Three direct boots staged→layer→staged without transient snapshot mode; verify EROFS for /usr,/etc,/var/lib/pacman,/boot, exact inventories, mount identities, persistent sentinels and ephemeral sentinels reset, no failed systemd units. This is a bounded lab layout, not production partitioning, UEFI selection, state migration/Flatpak/container validation, root authentication, privilege boundary against an administrator, or atomic activation. Separate state disk is a deliberate experimental isolation choice, not final product decision. See [Btrfs subvolume semantics](https://btrfs.readthedocs.io/en/stable/btrfs-subvolume.html) and [systemd random seeds](https://github.com/systemd/systemd/blob/main/docs/RANDOM_SEEDS.md).

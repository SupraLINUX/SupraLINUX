## Decisions

- Ubuntu 26.04 LTS is platform authority; KDE upstream stable is desktop authority.
- Qt provider selection follows KDE's requirement profile.
- SupraLINUX remains mutable and `.deb`/APT/dpkg based.
- GitHub-hosted Ubuntu 26.04 is **non-authoritative preflight** only.
- Authoritative build/test execution occurs inside disposable Ubuntu 26.04 **KVM VMs**.
- Each authoritative VM uses repository-scoped GitHub JIT configuration for one job; no persistent GitHub credential is baked into the golden image.
- Pre-merge self-hosted gates use controlled labels and reject fork PRs.
- The supported host recipe targets Ubuntu 26.04 amd64/x86_64 as infrastructure provider only and does not silently alter BIOS/firmware or force KVM-module reloads.
- The golden image is built from a signed/verified released Ubuntu image, records real provenance/hashes, is clone-cleaned offline, flattened/checked, and contains neither persistent GitHub credentials nor the temporary SupraLINUX build checkout.
- Host-local authoritative orchestration is serialized; queued/active authoritative workflows block new runner creation.
- JIT evidence is bound to one newly-created workflow run ID for the exact PR head SHA. Ambiguous attribution is a failure.
- Authoritative package builds use fresh `sbuild/unshare` isolation and capture `.deb/.changes/.buildinfo` before runtime tests.
- Nested KVM is a **runtime** gate: a minimal QEMU process must successfully initialize `-accel kvm -cpu host`.
- Authoritative `autopkgtest/QEMU` uses the repository's deterministic `qemu-kvm-required.sh` via `--qemu-command` and explicit x86_64 architecture. No TCG fallback is permitted by that wrapper.
- The QEMU wrapper SHA-256 is part of authoritative evidence.
- DAG states remain `PASS`, `FAIL`, `BLOCKED`; `BLOCKED` is never counted as `FAIL`.

## Inference

Ubuntu Qt 6.10.2 remains a strong reuse candidate for the current Plasma 6.7 profile, but matching the version line is not certification.

The hosted package-build path is proven and retained with evidence. Repository-side implementation now covers the intended Phase 1 chain from host preflight through verified source image, golden-image build, JIT lifecycle, exact workflow attribution, package build and deterministic KVM-only nested system test.

No repository-side validation can establish the remaining authoritative facts: actual nested KVM behavior on the intended host, real source/golden image hashes produced there, real runner-group authorization, and a real `autopkgtest/QEMU` PASS.

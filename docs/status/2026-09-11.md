### Signed source-image use-time re-verification

The repository now retains Ubuntu's `SHA256SUMS` and `SHA256SUMS.gpg` beside the downloaded cloud image. `scripts/verify-ubuntu-cloud-image-provenance.sh` re-runs `gpgv` immediately before the golden builder inspects/uses the source image, derives the expected image SHA from the freshly verified signed metadata, and requires both provenance and actual image bytes to match it.

The functional test uses an ephemeral GPG key and a real detached signature. It tests valid input plus rejection of changed image bytes, checksum metadata altered after signing, invalid provenance signature marker, duplicate provenance hashes, and jointly modified image/provenance without matching signed metadata.

## Decisions

- Ubuntu is platform authority; KDE upstream stable is desktop authority. Provider and authority remain separate.
- SupraLINUX remains mutable `.deb`/APT/dpkg.
- Hosted GitHub runners remain non-authoritative preflight.
- Authoritative jobs run in disposable Ubuntu 26.04 KVM/JIT guests.
- Nested KVM is a runtime requirement, not a label assumption.
- `autopkgtest/QEMU` must use the project KVM-only QEMU wrapper; TCG fallback cannot count as authoritative PASS.
- JIT jobs are serialized on the host, reject fork PRs, and bind evidence to one new workflow run ID for the exact PR head SHA.
- Golden source images must pass both fetch-time Ubuntu signature verification and use-time cryptographic re-verification before use.
- Repository Policy requires Bash syntax, ShellCheck, QEMU-wrapper functional tests, signed source-image functional tests, architecture invariants and live Qt verification.
- DAG states remain `PASS`, `FAIL`, `BLOCKED`; `BLOCKED` is not `FAIL`.

## Inference

Repository-side Phase 1 mechanics are now extensively validated, including signed-source re-verification. This does not prove actual nested KVM behavior, actual golden-image hashes, runner-group authorization, or authoritative package/system test results; those require real KVM execution.

GitHub's JIT endpoint does not expose `disableupdate`. Therefore runner installation version/hash are recorded at golden-build time and runtime diagnostics must preserve the effective version. No unsupported JIT update-control flag is assumed.
